**Rules for this file**
- Counts come **only** from saved outputs in [`notebooks/00_source_exploration.ipynb`](../notebooks/00_source_exploration.ipynb) (restored from git, not re-run) or from the scripts in [`sql/profiling/`](../sql/profiling/). "Cell N" refers to that notebook (0-based cell index). Script results were run on 2026-11-27 and 2026-11-28 against raw batch `cdaee7385083` (every raw table; rechecked 2026-11-28) and are quoted as `script → column = value`.
- No number is estimated or adjusted. If there is no saved evidence, the count is `TBD` and the evidence is a `TODO` pointing to the planned script in `sql/profiling/`.
- Bronze (`raw.*`) never fixes these issues. Everything is loaded as text (empty cells as NULL) and handled in Silver.

**Status**
- `verified`: the count is in a saved notebook output or a profiling script result.
- `partial`: the issue is visible in a saved output, but the full count still has to be proven.
- `unverified`: no saved evidence yet.

## Notes on the evidence

- **Grain (DQ01, DQ02):** every grain cell in the notebook (cells 11, 16, 21, 26, 31, 36, 41, 46, 51, 56) ran with `GRAIN = []` and printed `GRAIN is empty. Review the data and specify the key columns.`, so the notebook never confirmed a grain. The counts now come from `grain_src01.sql` and `grain_src05.sql`.
- **Return → sales line (DQ07):** `check_fk()` is defined in cell 60, but its only call is commented out, so it never ran. The count now comes from `fk_return_sales_line.sql`.
- **Resign date (DQ08):** `data_period.sql` shows every `resign_date` falls between 2024-05-24 and 2024-06-18, while every `Change_Log.effective_date` is 2024-07-01. `dq08_resign_rule.sql` query 2 shows the latest sale of any resigned employee is 2024-06-30, so the rejected 1-July rule would flag nothing and hide the issue. All 547 flagged lines fall between the resign date and 30 June (`lines_rule1_only = 547`). Per employee: EMP1035 161, EMP1051 108, EMP1046 79, EMP1070 62, EMP1048 45, EMP1054 37, EMP1075 33, EMP1100 22.
- **Unmapped customers (DQ10):** cell 59 also shows `SRC08/Sheet1 → SRC01/data customer_id orphans 0`, so every customer with a sale is in SRC08. The 157 unmapped customers have no sales in SRC01.
- **Data period (DQ19):** `check_data_period` was never committed (searched all branches); it is replaced by `data_period.sql`.
- **Off-territory and transfers (DQ09, DQ11):** `off_territory_sales.sql` query 3 shows every off-territory line belongs to a customer mapped to one of the 8 resigned employees (EMP1051 1,188 lines, EMP1035 947, EMP1046 701, EMP1048 574, EMP1070 435, EMP1075 131, EMP1100 115, EMP1054 101), sold from 2024-07-01 on. SRC08 was never updated after the resignations. The 5 transferred reps are not a cause: 0 off-territory lines are mapped to them, though they sell 276 of them.
- **Discount rounding (DQ14):** the stored `discount_amount` is always a multiple of 100 VND and equals the exact discount rounded half-to-even (banker's rounding, as Python `round(x, -2)`). Plain half-up rounding (Postgres `round()`) explains only 11,353 of the 13,971 mismatches. Over all rows the rounding nets to −590 VND.
- **Returns (DQ16):** the issue as planned does not occur at line level (0 returns). It only appears if returns are judged by the whole order (780), which DQ15 shows is wrong because `delivery_status` is line-level.
- **Target overlap (DQ18):** the 48 v1 H2 rows without a v2 row hold 10,743,800,000 VND. v2 raised the H2 target of the 103 remaining employees by 10,742,200,000 VND (`target_overlap.sql` query 4), so v2 appears to re-assign the resigned employees' targets. The rule is open in A-DQ18.
- **Mismatches with the planned figures:** none. DQ09 matches the plan figure of 4,192 exactly. The only other difference is rounding: the plan says "52%" null `tax_code` and the output shows 51.7%. DQ16 was planned as an issue but has 0 rows at line level.
